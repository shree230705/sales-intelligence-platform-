# Architecture

## Overview

The platform is a three-tier application:

```
React SPA  <-- JSON/HTTPS -->  Flask REST API  <-- PyMongo -->  MongoDB
                                      |
                                      +-- ML service (scikit-learn, loaded from disk)
```

## Backend layering

Requests flow through three layers, each with one responsibility:

- **routes/** — parse the HTTP request, call a service function, return a
  response via `utils/responses.py`. Routes never touch MongoDB directly.
- **services/** — business logic: validation rules, calculations (e.g. lead
  score classification, target achievement %), orchestration across
  collections.
- **models/** — schema definitions and any MongoDB-specific query helpers.

This separation exists so that, for example, the lead-scoring logic used by
`POST /api/ml/lead-score` can also be reused internally when a new lead is
created (auto-score on creation), without duplicating code across route
handlers.

## Application factory

`app/__init__.py` exposes `create_app(env_name)` instead of a module-level
`app = Flask(__name__)`. This is what makes `create_app("testing")` possible
in `tests/`, pointing the whole app at an isolated test database without
any test needing to monkeypatch a global.

## Authentication (Phase 3)

JWTs are issued on login and verified by a middleware decorator
(`@requires_auth`, `@requires_role(...)`) applied to protected routes. The
decoded user is attached to Flask's request-scoped `g` object so services
can check `g.current_user["role"]` for authorization decisions.

## ML serving

The model is trained offline by `backend/ml/train.py`, which reads
`data/sample_leads.csv`, engineers features, trains a classifier, and saves
it to `backend/ml/model.pkl` (git-ignored — regenerated by
`python ml/train.py` as part of setup, not committed). At request time,
`app/services/ml_service.py` loads the model once and reuses it for every
`/api/ml/lead-score` call — training never happens inside a request.

## Why these technology choices

| Decision | Reasoning |
|---|---|
| Flask over Django | Explicit, minimal — better demonstrates hands-on REST API design skills for a portfolio project. |
| MongoDB over a relational DB | Lead/opportunity records have variable, evolving fields (notes, free-text requirements); document storage fits naturally and demonstrates NoSQL skills. |
| Vite + React over Create React App | CRA is no longer actively maintained; Vite is the current standard for new React projects — faster dev server, simpler config. |
| JWT over server-side sessions | Stateless auth fits a decoupled SPA + API architecture cleanly. |
| Random Forest for lead scoring | Handles non-linear interactions between features (e.g. budget × industry) better than logistic regression, while still exposing feature importances for the "why this lead is ranked highly" explanation feature. Finalized in Phase 9 after inspecting the actual sample data. |

## Future improvements (tracked honestly, not implemented yet)

- Production frontend Docker stage (build + nginx) instead of the Vite dev server
- Redis caching layer for analytics aggregations
- WebSocket-based real-time notifications instead of polling
